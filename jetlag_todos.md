## Follow-up — not yet fixed at the source

| Item | Problem | Suggested fix |
|------|---------|----------------|
| `patch_yaml_scalar()` silent no-op | `sed` substitution on an existing line — silently does nothing if the target key isn't already present, no error. Root cause of the `operator_index_name` bug above: `all.rhoai-disconnected-bm.sample.yml` has no placeholder line for it, so `deploy_rhoai_bm.sh`'s auto-patch has been silently failing on *every* RHOAI disconnected run. | Add an `operator_index_name: ""` placeholder to the sample template, or make `patch_yaml_scalar` append the key when absent. |
| Step 6/7 resume-checks too coarse | `check_step_done` step 6 is just `[[ -f kubeconfig ]]` — `mno-post-cluster-install` writes it early, then has ~15 more tasks; dying anywhere after means `--resume` never re-enters the role. Step 7's check (`idms-operator-0` exists) has the same gap for the `rhoai-catalog-dev` CatalogSource alias created later in the same block — step 10 fails without it (olminstall hardcodes that source name). | Check a stronger completion signal per step (e.g. DSC existence for 6, `oc get catalogsource rhoai-catalog-dev` for 7), or split into finer-grained steps. |
| `mno-post-cluster-install`'s multi-catalog `when` logic | "Apply oc mirror catalogSource" (guarded by `when: not catalog_sources_stat.exists`) ran even though the mutually-exclusive sibling task (`when: catalog_sources_stat.exists`) had just succeeded moments earlier in the same play — confirmed via a direct `stat` module call that `exists: true` was correct. Routed around with `--start-at-task`; root cause not identified. | Reproduce in a minimal playbook to isolate whether it's a `register`/fact-scoping issue. |
| Audit for more bare `oc create` calls | The kube-burner SA fix was found by hitting it on a retry, not by inspection — sibling non-idempotent `oc create` calls may exist elsewhere in `mno-post-cluster-install`/`sno-post-cluster-install`. | Grep both roles for `oc create` (vs `oc apply`) and convert proactively. |
| `/dev/stdin` ad-hoc playbook pattern is broken | The skill's "Connection refused" recovery recipe (`ansible-playbook -i ... /dev/stdin <<'EOF' ... roles: [bastion-assisted-installer] ... EOF`) resolves `vars_files:` **and** `roles:` relative paths against `/dev`, not the invocation cwd — confirmed directly (a plain var came back undefined). As documented it would fail with "role not found". | Replace with the working pattern: write to a real temp file inside `ansible/` (e.g. `ansible/_adhoc-<name>.yml`), run it, `rm` it after. |
| `bastion-storage` "auto" mode + multi-VD hosts | A freshly-allocated host with an unconfigured PERC controller has no VDs at all — a real prerequisite step not covered by any preflight doc. Separately, once two VDs exist, "auto" processes `registry` before `nfs` and always grabs the *largest* unused disk — hands the big NFS-sized volume to the registry instead. Worked around with explicit `bastion_registry_disk`/`bastion_nfs_disk` device paths. | Document the RAID-VD-creation prerequisite in the preflight checklist; consider a size-aware or explicitly-ordered default. |

## Open Action Items

### J-6 — Investigate `Error: bad expression` in `dependent-operators/generate.sh`

`populate_rhoai_images()` sees 3 `Error: bad expression` messages from `dependent-operators/generate.sh`; `isc.yaml` output is still correct so this hasn't blocked runs. Suspected cause: `get_ocp_versions()` in `disconnected-imageset`'s `lib/utils.sh` uses a jq-style `keys[]` expression that may not be valid in Go yq v4, skipping the versioned-image loop (the unversioned fallback still produces a correct digest). Upstream fix needed in `disconnected-imageset`, not Jetlag. Cosmetic as long as no template uses the versioned placeholder form.

### J-7 — Handle missing `rhoai-{version}` directory in disconnected-imageset

`find_rhoai_version_dir()` warns and skips version-specific workbench/framework images when the mapped `imagesets/v2/rhoai-X.Y.GA` (or `.EAn`) directory doesn't exist upstream yet. No Jetlag code change needed — resolves automatically once `disconnected-imageset` adds the directory. Verified 2026-08-25 that this class of gap is often *not* actually missing content: the `rhoai-ci` source (FBC-image-driven) can independently cover the same images, sometimes more accurately than the version-specific directory would have. Check both before assuming a gap.

### J-8 — Provide bastion registry CA cert to DSCI (disconnected RHOAI install)

Open question on whether `image.config.openshift.io/cluster`'s `additionalTrustedCA` alone suffices for RHOAI components to trust `<bastion-fqdn>:5000`, or whether DSCI needs an explicit `spec.trustedCABundle` too. **Update 2026-08-25**: `deploy_rhoai_bm.sh`'s step 11 (`--add-custom-ca-bundles`) now patches DSCI `spec.trustedCABundle.customCABundle` directly with 4 bundles (registry, MinIO, PyPI cache, Git cache) and this has been confirmed working end-to-end on a live cluster (non-empty `customCABundle`, 6655 bytes). Likely resolved — downgrade to verify-and-close on the next deployment rather than open investigation.

### J-15 — Add NFS StorageClass + PersistentVolumes to post-deploy step

`bastion-rhoai-services` creates 80 NFS export dirs and starts `nfs-server`, but never creates the OpenShift `StorageClass`/`PersistentVolume` objects — any PVC requesting NFS storage stays Pending. Need: a `nfs-bastion` StorageClass (`kubernetes.io/no-provisioner`, `WaitForFirstConsumer`, `Retain`) plus 80 PVs pointing at `<bastion-ip>:/var/nfs/pv-100gb-{1..80}` (100Gi each). Skip condition for `--resume`: `oc get sc nfs-bastion`. Unblocks: `model-catalog-postgres` PVC → AI Hub model catalog → `LLMInferenceService` postgres backend.

Skip condition: secret exists.

### J-18 — Add `registry.stage.redhat.io` credentials and `rhaii` imageset coverage

`LLMInferenceServiceConfig` objects reference `registry.redhat.io/rhaii/vllm-{cuda,rocm,gaudi,spyre,cpu}-rhel9`, which aren't yet promoted to production — only `registry.stage.redhat.io/rhaii/` has them, and the bastion pull-secret has no stage credentials (confirmed via internal Jira: the `rhaii` namespace needs Customer Portal credentials, not a UHC pool token). Two-part fix: (1) add a `registry.stage.redhat.io` auth entry to `pull-secret.txt`; (2) add a `registries.conf.d/rhaii.conf` redirect (`registry.redhat.io/rhaii` → `registry.stage.redhat.io/rhaii`) to `sync_rhoai_registries_conf()`, plus the `rhaii/vllm-*` images to `additional_images` and a matching IDMS entry. Without this, any `LLMInferenceService` using a GPU accelerator fails to pull its serving image in a disconnected environment.
